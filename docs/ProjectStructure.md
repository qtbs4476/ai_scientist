## 一、项目概述

### 1.1 项目背景

当前人工智能正加速融入科学研究全过程（AI for Science）。传统科研模式高度依赖研究者的个人经验与文献积累，在面对海量数据、跨学科交叉和复杂系统时，往往效率低下且易陷入思维定式。大语言模型（LLMs）凭借强大的知识整合与逻辑推理能力，为科学发现提供了新路径——有望成为"AI Scientist"（人工智能科学家），自动提出新颖、可验证的科学假设，推动科研范式从"数据驱动"向"智能驱动"跃迁。

### 1.2 项目定位

基于国产开源大模型（Qwen / 千问）研发面向科学假设生成的 AI 系统，构建安全、开放、可持续的智能科研基础设施，服务国家科技自立自强战略。

### 1.3 核心目标

开发一个具备 **问题理解—知识整合—关联发现—可验证假设生成** 能力的 AI 系统原型，实现从"数据/文献输入"到"可验证科学假设输出"的智能闭环。

### 1.4 核心能力项（四大能力）

| 能力项            | 能力描述                                   |
| -------------- | -------------------------------------- |
| **文献挖掘与事实提取**  | 结合选题的结构化信息，提取关键科学事实，避免断章取义             |
| **逻辑驱动的假设生成**  | 利用归纳与演绎推理，基于已知事实生成初步假设                 |
| **论证可行与多轮迭代**  | 挖掘跨学科技术迁移潜力，确保引用真实可靠、假设具备可行路径，多轮迭代完善提案 |
| **智能体思辨与人在回路** | 构建可交互、具备教学意义的人机协作流程，对假设进行辩论与迭代         |

### 1.5 Agent 与千问模型的协作关系

> **核心原则**：千问做底层大模型能力底座，团队自主开发整套 Agent 架构与科研业务流水线，Agent 全程调用千问完成各类语义任务。

- **千问 Qwen 是唯一底层基座**：所有智能体的语义理解、文献阅读、推理、文本生成能力必须依托阿里云百炼 API 调用千问开源系列（Max/Plus/Turbo 等），不能换其他大模型；可对千问做领域 SFT 微调，但模型本体仍是千问。

- **团队自主开发上层 Agent 模块**：千问只提供基础大模型能力，多智能体/超级智能体的调度逻辑、数据处理流水线、领域专用工具、迭代校验、人在回路交互、前端可视化等全部为参赛团队自研模块。

### 4.2 模块详细设计

#### 模块1：文献挖掘与知识整合模块 (Literature Miner)

- **职责**：解析上传文献、提取关键事实、构建语义索引

- **自研部分**：文本清洗、结构化抽取科学事实、过滤无效信息

- **千问调用**：读取论文/领域数据，完成语义理解与实体识别

- **子功能**：

  - PDF/文本解析器：提取文献元数据和正文内容

  - 实体关系抽取：识别人物、方法、数据、结论等要素

  - 向量嵌入生成：将文献段落转化为语义向量

  - 跨文献关联发现：识别不同文献间的引用、矛盾、互补关系

- **输入**：文献文件(PDF/文本)、研究领域关键词

- **输出**：结构化文献知识图谱、语义向量索引

#### 模块2：逻辑驱动假设生成模块 (Hypothesis Generator)

- **职责**：基于整合知识，通过归纳+演绎逻辑生成可验证假设

- **自研部分**：逻辑自洽校验、假设候选筛选

- **千问调用**：执行归纳/演绎推理产出初始科学假设

- **子功能**：

  - 问题理解器：解析用户研究意图与约束条件

  - 归纳推理引擎：从具体文献事实中提炼普遍规律

  - 演绎推理引擎：基于已知理论推导新结论

  - 假设候选生成器：产出多个候选假设供筛选

- **输入**：结构化文献知识、用户问题描述

- **输出**：候选假设列表（含证据链引用）

#### 模块3：双辩论智能体对抗模块 (Debate Agents)

- **职责**：通过正反方对抗思辨，消除假设片面性与偏见

- **自研部分**：多轮循环调度、辩论流程控制

- **千问调用**：承接正反方论点生成与人工反馈处理

- **子功能**：

  - 正方Agent：论证假设合理性，补充支持证据

  - 反方Agent：寻找假设漏洞，提出反例与质疑

  - 裁判Agent：评估双方论点，裁定假设质量

  - 迭代修正器：基于辩论结果自动修正假设表述与适用范围

- **输入**：候选假设、文献知识库

- **输出**：经辩论打磨的优化假设（含正反双方证据记录）

#### 模块4：原文溯源校验模块 (Source Traceability)

- **职责**：确保假设引用真实可查，避免断章取义与虚构引用

- **自研部分**：向量相似度比对算法、冲突检测逻辑

- **千问调用**：辅助语义冲突判定与重写

- **子功能**：

  - 引用绑定器：生成假设时强制关联原文段落ID

  - 向量相似度比对：自动检测假设表述与原文的语义冲突

  - 冲突检测器：标记与原文矛盾的假设陈述

  - 漏洞回传器：将冲突信息反馈给思辨Agent重写

- **输入**：待校验假设、文献向量库

- **输出**：校验通过的假设 / 冲突报告

#### 模块5：因果量化检验模块 (Causal Quantitative Test)

- **职责**：通过统计方法验证假设的因果关系，排除循环论证与无依据猜想

- **自研部分**：数据指标提取、统计分析脚本

- **千问调用**：辅助指标识别与结果解读

- **子功能**：

  - 数据指标提取器：从数据集中提取关键变量指标

  - 相关性分析器：计算变量间的统计相关性

  - 显著性检验器：进行分组显著性差异检验

  - 因果判定器：基于统计结果判定假设是否成立

- **输入**：待检验假设、相关数据集

- **输出**：因果验证结果（支持/不支持）、统计检验报告

#### 模块6：配套约束Prompt模块 (Prompt Guardian)

- **职责**：通过Prompt工程低成本约束模型输出质量

- **约束规则**：

  - 禁止脱离事实/法条主观推断

  - 严格区分"相关性"与"因果性"，不随意归因

  - 结论必须限定适用场景，禁止绝对化表述

  - 强制要求引用真实文献，标注来源

  - 输出结构化格式模板（10个标准字段）

- **实现方式**：System Prompt + Few-Shot 示例 + 输出Schema约束

| 人工干预 | POST | `/api/debate/intervene`       | 用户在思辨过程中介入指导    |

### 5.5 关键Prompt工程

#### 假设生成约束Prompt结构：

```
System: 你是一位严谨的科学研究员，必须遵守以下规则：
        1. 所有结论必须基于引用的文献证据
        2. 区分相关性与因果性，不得随意归因
        3. 结论须限定适用条件，禁止绝对化表述
        4. 参考文献必须真实可查，标注完整来源

User: 基于以下文献摘要，针对问题"{user_question}"，
      生成一个可验证的科学假设。
      文献摘要：{literature_context}

Output Schema:
{
  "hypothesis": "假设表述",
  "evidence_chain": [{"claim": "论点", "source": "文献ID", "quote": "原文引用"}],
  "scope": "适用范围限定",
  "verification_plan": "验证方案"
}
```

#### 辩论Agent对抗Prompt结构：

```
System (正方): 你是正方辩手，任务是论证以下假设的合理性。
              你必须引用文献中的具体证据来支持论点。

System (反方): 你是反方辩手，任务是找出以下假设的漏洞。
              你必须引用文献中的反例或矛盾证据来反驳。

User: 待辩论假设：{hypothesis}
      可用文献：{literature_pool}

Output: {
  "round": 回合数,
  "pro_arguments": [正方论点列表],
  "con_arguments": [反方论点列表],
  "judge_verdict": "裁判裁定",
  "refined_hypothesis": "修正后假设"
}
```

## 六、开发流程

### 6.1 阶段总览

项目开发分为 **4 大阶段**，覆盖从前期准备到终审提交的完整生命周期。

```
阶段1：前期准备  ──▶  阶段2：核心研发  ──▶  阶段3：模型优化与工程落地  ──▶  阶段4：测试与提交
(报名+资源申领)       (多智能体架构开发)     (SFT微调+前端+演示)            (测试+文档+答辩)
```

### 6.2 阶段1：前期准备（资源申领）

**目标**：搭建开发环境，确定选题方向。

| 序号  | 任务               | 负责方      | 交付物            |
| --- | ---------------- | -------- | -------------- |
| 1.1 | 申领阿里云算力补贴，开通百炼平台 | 后端/AI工程师 | 百炼API凭证、调用截图留存 |
| 1.2 | 获取千问模型 API 调用凭证  | AI工程师    | API Key、调用凭证截图 |
| 1.3 | 确定赛道方向与细分研究领域    | 全员讨论     | 选题确认书          |
| 1.4 | 收集合规领域数据集、权威参考文献 | 领域专家     | 数据集清单、文献库      |
| 1.5 | 搭建项目脚手架、开发环境     | 后端工程师    | 项目仓库初始化        |

### 6.3 阶段2：AI Scientist 多智能体架构开发（核心研发）

**目标**：自研分层 Agent 流水线，每一步均调用千问执行语义任务，自研代码负责调度、清洗、校验、循环迭代。

#### 2.1 文献挖掘 Agent 开发

- 调用千问读取论文/领域数据

- 自研代码完成文本清洗、结构化抽取科学事实、过滤无效信息

- 构建向量索引，支持语义检索

#### 2.2 推理假设生成 Agent 开发

- 输入提取事实，千问执行归纳/演绎推理产出初始科学假设

- 自研模块做逻辑自洽校验

- 输出候选假设列表（含证据链引用）

#### 2.3 跨学科迭代论证 Agent 开发

- 自研逻辑实现多轮循环

- 调用千问检索交叉领域文献，验证假设可行性、补充实验路径

- 多轮迭代完善提案

#### 2.4 思辨人机交互 Agent 开发（人在回路）

- 自研交互前端/接口

- 千问承接人工反馈，对假设、实验方案反复辩论优化

- 支持用户介入评论、指导修正方向

#### 2.5 标准化输出 Agent 开发

- 自研格式化模块

- 调用千问按赛事规范生成完整《科学假设与研究计划》全套标准化字段内容

- 输出格式（10个必填字段）：待研究问题、解决思路、技术手段、数据集（Source+Target）、标题、摘要、方法论、实验设计、实验结果、参考论文

#### 2.6 验证校验模块开发

- 双辩论智能体对抗模块（正反案例对抗思辨）

- 原文溯源校验模块（引用绑定+向量比对+冲突检测）

- 因果量化检验模块（统计校验脚本）

- 配套约束Prompt模块（领域规则约束）

### 6.4 阶段3：模型优化与工程落地

**目标**：通过 SFT 微调提升垂直领域适配度，完成前端与演示材料。

| 序号  | 任务                       | 负责方   | 交付物             |

| 3.2 | 提升垂直科研领域适配度              | AI工程师 | 评估报告（领域任务指标）    |
| 3.3 | 搭建可交互前端页面                | 前端工程师 | 前端应用            |

## 九、风险管理

### 9.1 风险识别与应对

| 风险类别     | 风险描述          | 影响程度 | 应对措施                      |
| -------- | ------------- | ---- | ------------------------- |
| **技术风险** | 千问API调用不稳定/限流 | 高    | 实现重试机制、请求限流、缓存常用结果        |
| **技术风险** | 假设生成质量不达预期    | 高    | 多轮辩论迭代 + 约束Prompt + SFT微调 |
| **技术风险** | 文献引用虚构问题      | 高    | 原文溯源校验模块强制绑定 + 向量比对       |
| **数据风险** | 领域数据集获取困难     | 中    | 提前联系领域专家、使用公开数据集          |
| **进度风险** | 核心模块开发延期      | 中    | 模块化解开发、设置里程碑缓冲期           |
| **合规风险** | 数据来源不合规       | 中    | 严格审核数据来源、留存来源说明           |
| **科学风险** | 假设科学性不足       | 中    | 领域专家全程参与审核                |
| **演示风险** | 现场演示失败        | 中    | 录制备份视频、准备离线演示方案           |

### 9.2 质量保障措施

1. **代码质量**：代码评审 + 单元测试 + 集成测试
2. **科学性保障**：领域专家审核假设的科学性与合理性
3. **可复现性**：Docker容器化部署 + 详细部署文档
4. **凭证完整性**：专人持续整理API调用截图、数据来源、文献引用
5. **文档同步**：代码与文档同步更新，避免文档滞后

### 《科学假设与研究计划》模板

系统最终生成的《科学假设与研究计划》需包含以下标准化字段：

```markdown
# 《科学假设与研究计划》

## 1. 待研究问题 (Problem Statement)
[明确指出当前领域存在的具体局限性]

## 2. 解决思路 (Rationale)
[基于逻辑推理的创新点阐述，展示推导链条]

## 3. 必要的技术手段 (Technical Details)
[详细列出验证假设所需的具体技术栈：统计与机器学习、深度学习方法等]

## 4. 数据集 (Datasets)
- **Source**：[假设推演依据的历史数据，来源合规真实]
- **Target**：[验证实验所需的拟采集数据特征]

## 5. 标题 (Paper Title)
[符合学术出版规范的标题]

## 6. 摘要 (Paper Abstract)
[包含背景、方法、预期结果的完整摘要]

## 7. 方法论 (Methods)
[具体的实施步骤，包括模型架构或实验流程]

## 8. 实验设计 (Experiments)
[包含基线对比(Baselines)及评估指标(Metrics)]

## 9. 实验结果 (Results)
[通过公式推导或实际执行，在一定范围内验证该实验可行性]

## 10. 参考论文 (References)
[系统生成假设所引用的真实文献列表，严禁虚构]
```
